- 处置：bulkBar 中 order_frame/order_inv 的「模板」「导入」按钮渲染 disabled 灰态、点击无效；金蝶导入（预检流程，安全）保留；其余表单模板/导入未动。
- 隐患（待修，仅反馈未执行）：importXLSX 单表单/全量导入两路径仅在 `newData.length===0` 时拦截，但空表头+空数据行会得到 length>0 的空对象数组，仍会 save 覆盖；缺预检/确认/导入前自动备份。同类高危：顶栏「全量导入」(triggerImport() 无 formKey) 一次清空所有表单；非订单表单的「导入」同样有此 bug；「恢复」(.json) 误选文件会整体替换（设计如此但无二次确认）。低危：删除/批量删除仅删选中行。
- 待修项（用户未下令）：importXLSX 增加「全空行过滤 + 覆盖前确认弹窗 + 导入前自动备份」；或复用金蝶导入的预检-确认模式统一导入入口。

## importXLSX 导入加固（commit deaa65b，已部署 build 2026-08-22.26）
- 用户下令执行：把 importXLSX 改为「过滤全空行 → 0 条有效数据中止 → 覆盖前确认框 → 导入前自动备份」。
- 新增辅助函数：`importPreBackup()`（覆盖前自动下载全量 .json，文件名含时间戳，顶部「恢复」可还原）、`currentDataCount(varName)`（取表单现有记录数）、`rowHasData(obj,keys)`（至少一个已映射字段非空）。
- 四道保险（单表单 + 全量导入均应用）：
  1. 表头匹配校验：`colKeys.filter(Boolean).length===0` → 中止（防错文件映射成空对象覆盖，这是空/错文件灾难的根因）。
  2. 全空行过滤：每行需至少一个已映射字段非空才计入；最终 `newData.length===0` → 中止。
  3. 覆盖前确认框：`confirm('将导入 N 条并覆盖现有 M 条…')`，取消则不写库（仅当现有记录数>0 时弹）。
  4. 导入前自动备份：`importPreBackup()` 在确认后、save 前下载当前全量数据 .json。
- 验证：node 模拟——「错表头文件」→ 中止(无匹配表头)；「模板式全空行」（解析器先过滤空行）→ 中止(0条有效数据)；两类灾难场景均不再静默覆盖。语法校验通过。
- 注：订单「模板/导入」按钮仍 disabled（build .25），本加固让其余表单的导入及顶栏「全量导入」不再有覆盖风险。

## 打通产品库存与库存订单已交付数量（commit 8777b7f，已部署 build 2026-08-22.26）
- 用户需求（选方案2+改名）：产品主数据「库存」改名「库存/已交付数量」；库存 = 全部库存订单明细已交付数量之和（库存订单=生产入库，交付多少即多少库存）。
- 根因：订单明细行 `deliveredQty` 配置 `locked:true`（录入弹窗只读）→ 恒为 0；`syncStockFromInvOrders()` 仅在 `deliveredQty>0` 时写入 → 同步空转，库存保持手动录入值，两边脱节。
- 改动：① `stock` 字段 label 三处（defaultFields 606、migrateProductDailyCap 注入 1627、产品选择器 2144）改名「库存/已交付数量」，保持 `locked:true`（由交付量驱动）；② 订单明细行 `deliveredQty` 改 `locked:false`，录入弹窗可填（orderItemRow 的 else 分支本就渲染可编辑 number，解锁确保不被系统字段逻辑锁死）；③ 重写 `syncStockFromInvOrders()`：含 0 值也同步（有库存订单的产品 stock=Σ已交付，无库存订单的保留手动库存）；④ 新增 `backfillInvDeliveredFromStock()` 一次性迁移：把现有库存按订单量比例反填到对应库存订单已交付数量（仅对「已交付合计=0 且库存>0」的产品，幂等），于 initApp 中在 sync 前调用，避免同步后库存被清零。
- 服务器真实数据验证：37 产品 / 11 库存>0 / 27 库存订单 / 库存订单已交付合计=0 —— 与用户描述一致；迁移在浏览器打开页面时经 save() 落库（幂等），无需手动干预。
- 部署：本地 git commit（deploy.sh/deploy.bat 不入 git，含服务器信息），`bash deploy.sh` scp 上传 + nginx reload；线上版本 build 2026-08-22.26。
