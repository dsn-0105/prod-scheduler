### 原始需求复述（用户原话）

> 在页面左上角"生产排单系统"做一个下拉栏，可以点击下拉切换到质量系统（后续可能会新增其他系统）。质量系统内先只做一个表单"异常台账"，台账为表格形式，类似于订单管理列表，拥有字段"日期、编号"（目前只需要这两个，后续再新增），拥有操作"全选、新增、编辑"。"员工管理"里加那一行权限。

### 已拍板的技术方向（作为约束，本 PRD 不推翻）

1. 质量系统是**独立系统**，独立前端入口 `/quality/`、独立后端进程 `qa-server`（端口 3001）、独立数据文件 `data-qa.json`、独立版本号。
2. 生产系统 `server/server.js` **一行都不改**。
3. 两系统共用同一域名与同一套账号密码，**用户只登录一次**。
4. 员工管理面板新增权限点：权限键 `qa`，显示名「质量管理」；勾选=可编辑、不勾=只读。

## 二、产品目标

1. **独立**：质量系统与生产系统在代码、进程、数据三层面完全脱离，生产系统零风险；任何质量系统的故障、重启、数据误操作都不影响生产排单。
2. **零学习成本**：质量系统的外观、交互范式（勾选→点工具栏按钮、列头排序、分页、弹窗编辑）与生产系统逐项一致，用户不需要第二个心智模型；切换系统只多一次点击，且登录态无感延续。
3. **可扩展**：新增"系统"只需在一个前端常量数组里加一行；新增"异常台账字段"只需加一条列定义 + 一个表单项。两处扩展都不要求改数据库、不要求改后端逻辑、不要求动生产系统。

## 三、用户故事

1. 作为**车间班组长**，我想在左上角"生产排单系统"标题上点一下就能切到质量系统，这样我不用记住第二个网址、也不用再登录一次。
2. 作为**质量员**（有 `qa` 权限），我想新增一条异常记录，日期默认今天、编号自动生成，这样我录一条只要点两次。
3. 作为**质量员**，我想勾选一条记录后点"编辑"改掉录错的日期，这样我不必删除重录、也不必麻烦管理员。
4. 作为**PMC / 生产经理**（无 `qa` 权限），我想进质量系统看异常台账，这样我查历史异常不用找人代查；但我改不了数据，页面上也看不到"新增/编辑"按钮。
5. 作为**管理员**，我想在员工管理里给某个人勾上"质量管理"，这样他能录异常记录；不勾的人只能看。

## 五、页面结构与交互说明

### 5.1 生产系统的系统切换下拉（改造点：`index.html` 第 301 行 `<h1>` 内）

**现状**：`<h1><svg…/><span>生产排单系统</span></h1>`

**改后结构（文字描述）**：
- `<h1>` 内部保持 `svg 图标 + <span>生产排单系统</span>` 不变，外面套一层可点击容器，并在 `<span>` 后追加一个 **12px 的下箭头 `▾`**。
- 点击容器 → 在 `h1` 下方绝对定位弹出面板（`z-index` 高于 `.nav`）。面板最小宽度 180px，`max-width: calc(100vw - 32px)`，不超出视口。
- 面板项：`图标 + 系统名 +（当前系统追加 ✓ 并高亮主色）`。当前项**可点击但只关闭面板**（不跳转、不刷新）。
- 关闭方式：点击面板外任意位置、按 ESC、点击当前项。
- **切换行为**：`location.href = 目标 url`（本标签页）。切换前**不弹确认框**——只有两列字段、编辑为弹窗式，误触概率极低，加确认是冗余。

**侧边栏收起态（F12，必须处理）**：
- 收起后标题文字被 CSS 隐藏，**只剩 svg 图标**。此时图标即切换入口：`cursor:pointer` + `title="切换系统"`；点击后下拉面板从图标**右侧**浮出（`left:100%; top:0`），避免被 56px 宽的侧边栏裁切。

**移动端（≤768px）**：
- 侧边栏为抽屉形态，标题在抽屉内完整可见，下拉在抽屉内正常向下展开。
- **不在**移动端顶栏 `#mobile-header` 另加切换入口——全站**只有一处**系统切换入口，避免两套心智。
- 抽屉内展开下拉时不自动关闭抽屉。

**"是否记住上次选择"——决策：不记住。**
理由：URL 本身就是唯一真实的状态源（`/` = 生产排单系统，`/quality/` = 质量系统）。若额外记忆"上次选择的系统"，用户从收藏夹/历史记录打开 `/` 却被强制跳到 `/quality/`，会认为是 bug；且两套状态（URL + 记忆）必然产生分歧。默认入口 `/` 恒为生产排单系统。

**可扩展的候选清单设计**：
```
SYSTEMS = [
  { key:'prod', name:'生产排单系统', url:'/',         icon:'house'  },
  { key:'qa',   name:'质量系统',     url:'/quality/', icon:'shield' }
]
```
- 一个前端常量数组（硬编码），**不引入数据库/后端配置/管理界面**。
- 后续新增"设备系统/采购系统"：在该数组加一行 + 部署对应页面。若要调整顺序，改数组顺序即可。
- 质量系统页面持有一份同结构的 `SYSTEMS` 副本（`prod` 项的 url 指回 `/`）。
- 为什么不放后端配置：10 人内部系统，一年多新增一个系统，硬编码的维护成本远低于一套配置读取/校验/兜底逻辑；且配置读不到时下拉会空掉，属于把简单问题复杂化。

### 5.4 「全选」的语义与用途 —— 明确结论

**语义**：工具栏最左侧的 `☐ 全选` 复选框，勾选后选中**当前页全部行**（与生产系统 `toggleSelAll` 完全一致，F7）。再次点击清空。这不是表头复选框（表头首列只有列宽位，不含全选框）。

**它与用户需求的对应关系**：用户原话"拥有操作'全选、新增、编辑'"，与生产系统「零部件数据」页工具栏注释里记录的按钮序列（"全选、编辑、复制、删除、新增、导出选中、入库"）**完全同构**。结论：用户描述的就是这套工具栏，全选即工具栏复选框，不是新发明的功能。

**选中之后做什么 —— 必须有落点，不做空占位**：
1. **导出选中（P1，但与全选同批交付）**：把选中行导出为 CSV（UTF-8 BOM，Excel 直接打开），位置在工具栏「删除」之后、`已选 N 项` 之前，与生产系统 `bulkExport` 位置一致。这是全选在当前阶段**唯一有实际意义的动作**，也是只读用户唯一可用的批量动作。
2. **删除（P1）**：受动作键 `qa.del` 门控。
3. **编辑（P0）**：只吃单条，多选即拒绝。

**结论**：全选不是"为未来预留的空按钮"。它当前的价值锚点是「批量导出」——只读用户勾几行导成表格发出去，是真实场景。因此 **P0 交付「全选」复选框 + `已选 N 项` 计数 + 行高亮，P1 紧接着交付「导出选中」**；若开发排期必须砍，砍「导出选中」会导致全选在 P0 阶段短暂空转，此时应同步把全选一起延后到 P1，而不是留一个点了没反应的复选框。

**是否需要删除功能 —— 决策：需要，P1（见 Q1）**
- 理由：`编号` 不可改，`日期` 可改。日常误录 90% 是日期选错，用「编辑」即可纠正，所以**编辑足以兜住绝大多数误录，删除不是 P0 阻塞项**。但"整条本不该存在"（重复录入、测试录入、非本厂异常）无法用编辑消解，必须有删除，否则台账被永久污染。
- 形态：沿用生产系统口径，**硬删除 + `confirm` 二次确认**（提示"确认删除 YC-20261123-00003（2026-11-23）？删除后不可恢复。"），不做软删除/回收站（10 人内部系统，引入软删除要同步改列表过滤、编号去重集合、导出范围，收益不抵成本）。
- 权限：注册动作键 `FORM_ACTS.qa = { del:'删除异常记录' }`，`formToKey('qa')` 原样返回 `'qa'`，因此**无需改任何权限函数逻辑**即可在员工面板右栏出现该动作勾选项。默认随表单写权限全开（`canAct` 宽松期口径，F11），管理员可单独收回。

### 5.6 排序与筛选（【build .166】仿订单管理列表 · 用户 2026-11-27 拍板 Q1A~Q5A）

**排序**
| 项 | 口径 |
|---|---|
| 范围 | **9 列全部可排**（含长文本列）|
| 交互 | 点列头，**三态循环**：升序 → 降序 → 取消（回默认 `日期 DESC`）。显示 ▲/▼，未排序列显示 ⇅ |
| 类型感知 | `num` 按数值（`9` < `100`，不是字典序）；`date` 按 `YYYY-MM-DD` 串序（≡ 时间序）；`text`/`long` 按 `localeCompare('zh-CN')`（中文拼音序，与生产 `cmpByColDef` 同口径）|
| 空值 | **恒沉底**（升序降序都在最后），且不随方向翻转。这是与生产系统的**唯一刻意差异**：生产的 `num('')=0` 会把空当最小值，而台账数量列经常整列空着，升序时一排空值糊在表头下面 = 把「未填」误报成「最少」|
| 二级键 | 恒为 `no DESC`（全序稳定，翻页不跳行），且**不随主键方向翻转** |

**筛选模式（三类型）**
| 列类型 | 模式 | 数量 |
|---|---|---|
| 文本（编号、产品名称、规格型号、异常描述、原因分析）| 包含 / 不包含 / 等于 / 不等于 / 以…开始 / 以…结束 / 为空 / 不为空 | 8 |
| 数量（总数量、检测数量、异常数量）| 大于等于 / 小于等于 / 等于 / 不等于 / **为空** / 不为空 | 6 |
| 日期（日期）| 今天 / 本周 / 本月 / 上月 / 过去一个月 / 过去三个月 / 从…到… / 等于 | 8 |

- 数量列的「为空/不为空」是**对生产的有意扩展**（生产数字列只有 4 模式）。理由：台账数量列经常整列空着，
  没有它就筛不出「还没填检测数」的记录 —— 这恰恰是质量台账最常见的追问。
- 周起点 = **周一**（与生产 `getWeekStart` 同口径）；`过去一个月/三个月` 用自然月加减并**含下界**（>=）。

**面板与反馈**
- 点表头漏斗 → 浮层（宽 230px，标题「筛选：<列名>」+ 模式下拉 + 输入框 + 取消/清除/确定）。
- 日期「从…到…」显示双日期框并隐藏单值框；为空/不为空/日期快捷模式**隐藏输入框**（不需要值）。
- 需要值的模式输入框为空时点确定 ⇒ **等同清除该列筛选**（不写入"看起来生效其实无效"的条件）。
- 该列有筛选时漏斗**变蓝加底色**（`.filt-ico.on`），判据与筛选有效性**同源**（`CORE.filtActive`，禁第二份）。
- 表格上方出现 chips 条：`总数量 ≥100 ×`，点 × 去单条，「清除全部」一次清空。
- 筛选后分页计数改为 **「筛选后 X / 全部 Y 条」**；无匹配显示「当前筛选条件下没有匹配的记录」+ 清除入口。
- **筛选状态仅内存**（Q3A）：刷新即清，不落 `localStorage`（避免"昨天筛过的东西"明天悄悄生效）。

**与「全选 / 导出选中」的联动（Q4A）**
- 筛选变化时**自动清掉被筛掉行的勾选**，否则先全选 100 条再加筛选只剩 3 条时，
  「导出选中」会导出 97 条肉眼不可见的行 —— 最容易让人以为系统坏了的一类问题。
- **排序不清勾选**（排序不改变可见集合，清了会变成"排个序勾选全丢"）。
- 唯一收尾入口 `afterFiltChange()`：关浮层 → 清隐藏勾选 → 回第 1 页 → 重绘。

**实现分工（禁第二份实现）**
- 判定全部在 `qa-core.js`：`matchFilter` / `applyFilters` / `filtActive` / `filtModesOf` / `modeNeedsVal` /
  `FILT_MODES_TEXT|NUM|DATE` / `FILT_MODE_NAME` / `weekStartOf` / `addMonthsStr` / `cmpTyped`，均为纯函数可单测。
- DOM 层 `qa-app.js` 只负责收集条件、拼面板/chips；**一行匹配逻辑都不许写在那里**。
- `qa-core.sortRecords` 扩成 `(list, key, dir, types)`，**向后兼容**：不传 `types` 时与 .165 逐字一致。

**明确不做**
- 列内复选框多选（生产仅对 `select` 类列启用；台账无 select 列，文本模式更精确）。
- 筛选状态跨会话记忆、列宽拖拽（后者仍属 P2-2）。
- 跨列模糊搜索框。

- 列表/CSV：`undefined` / `null` 一律渲染空串，不会出现 `undefined` 字样。

**排序范围**：~~仍只有 `date` / `no`~~ → **【build .166】9 列全部可排 + 可筛**（见 §5.6）。
`qa-core.sortRecords` 已扩成类型感知（`num` 按值 / `date` 按串 / `text` 按拼音），不传 `types` 时行为与 .165 逐字一致。

**编号不由人工填写**——这是本 PRD 对歧义点 ③ 的明确结论。人工填编号会带来：格式不统一、重号、与既有编号体系冲突、无法去重。系统自动生成 + 只读展示，与交付计划 `planNo`（"系统生成、必填、全局唯一、不可修改"）完全同口径。

**日期允许修改**——`编号` 不可改但 `日期` 可改，意味着"日期录错"可以自纠，但编号的日期段不会跟着变。这是**有意为之**：编号是记录的外部引用标识，改号等于断链；编号中的日期只是发号当日的批次信息，不是业务语义。**需要在"使用说明"里向用户说明这一点**，否则用户会疑惑"我把日期从 22 号改成 23 号，编号怎么还是 22 号"。

### 6.2 数据层内建字段（不占列、不上表单）

| 字段 | key | 说明 |
|---|---|---|
| 内部主键 | `id` | `qa-server` 生成（时间戳+随机），保证 `no` 万一被改也能定位记录 |
| 创建人 | `createdBy` | 登录用户名 |
| 创建时间 | `createdAt` | ISO 8601 |
| 最后修改人 | `updatedBy` | 登录用户名 |
| 最后修改时间 | `updatedAt` | ISO 8601 |

**明确声明**：这 5 个字段**不是**"塞给用户的字段"，它们不出现在表单、不出现在列表列、不占用任何 UI。存在的唯一理由：质量台账是追溯性质的数据，将来一定会被问"这条谁录的、什么时候录的"。现在落库成本近乎为零，将来补历史数据不可能。
P0 只落库；P1 在编辑弹窗底部以一行灰字展示"最后修改：张三 2026-11-23 10:12"。

**明确不加**用户没要求的字段：异常类型、涉及订单、责任部门、责任工序、处理状态、处理结果、附件、整改措施。候选清单见 Q4，**默认不加**。
（`异常数量`（`defectQty`）在 .165 之前属于本清单的「不合格数量」，本轮由用户明确要求纳入，已从"不加"清单移出。）

### 6.3 编号生成规则（`YC-YYYYMMDD-XXXXX`）

| 项 | 规则 |
|---|---|
| 前缀 | `YC`（"异常"拼音首字母，2 位大写字母，与 `PTH`/`XSDD`/`KCDD`/`JFJH` 同构）。与现有全部前缀无冲突 |
| 日期段 | 取**发起新增当日**（不是用户填的 `date`），`YYYY-MM-DD` 去掉横线 |
| 序号 | 5 位，左补零，**每日从 00001 重新开始** |
| 生成算法 | 照抄 F5 单源公式：扫描本表全部 `no`，筛出 `YC-<当日>-` 前缀的记录，取序号最大值 +1；再用"已用编号集合"做 `while` 去重兜底 |
| 单源要求 | 工程内**只允许存在一份** `nextQaNo()` 实现（前端预生成 + 服务端终检都调同一个函数的同一份代码，服务端持有权威版本） |
| 并发防重 | **服务端落库时做唯一性终检**：若提交的 `no` 已存在 → 返回 `409 {conflict:true, suggest:'YC-…-00005'}`；前端拿到 409 后静默用 `suggest` 重提交一次，用户无感。1~3 人并发下这条兜底足以保证**绝不重号** |
| 不可变 | 创建后任何路径（编辑、导入、恢复）均不得修改 `no` |
| 格式校验 | 服务端落库前校验 `/^YC-\d{8}-\d{5}$/`，不匹配直接 400（防脏数据涌入） |

### 6.4 数据文件结构（`data-qa.json`）

```
{
  "version": "qa-2026-11-23.1",
  "revs":    { "qaLogs": 0 },
  "qaLogs":  [
    { "id":"…", "no":"YC-20261123-00001", "date":"2026-11-23",
      "createdBy":"zhangsan", "createdAt":"2026-11-23T09:12:00+08:00",
      "updatedBy":"zhangsan", "updatedAt":"2026-11-23T09:12:00+08:00" }
  ]
}
```
- 版本号规则：`qa-YYYY-MM-DD.N`，与生产系统 `build` 版本号解耦（独立发版）。
- 写入：临时文件 + `rename` 原子替换；写入前保留上一版为 `data-qa.json.bak`。
- 读不到/损坏时：**拒绝启动并打印错误**，不要静默初始化空文件（否则一次磁盘故障会把全部台账抹掉）。

## 七、权限矩阵

### 7.1 权限点定义

| 权限键 | 显示名 | 归属 | 语义 |
|---|---|---|---|
| `qa` | 质量管理 | 员工管理 · 表单写权限 | 勾选 = 质量系统可编辑；不勾 = 只读 |
| `qa.del`（动作键） | 删除异常记录 | 员工管理 · 表单写权限 → 点「质量管理」右栏 | 控制「删除」按钮；归属表单 `qa` |

- 登记方式：`PERM_FORMS` 追加 `qa:'质量管理'`；`FORM_ACTS` 追加 `qa:{del:'删除异常记录'}`。`formToKey('qa')` 原样返回 `'qa'`，**无需改任何函数逻辑**（F10）。
- **向后兼容 / 上线操作**：`qa` 权限点上线后，存量员工的 `perms` 里没有 `qa` 键 → 一律按**只读**处理（`perms.qa === true` 才可写）。因此上线首日除管理员外全部只读，**必须由管理员在员工管理里逐个勾选「质量管理」**。此为预期行为，需在发版说明中写明，否则用户会报"点不了新增"。

### 7.2 操作权限矩阵

| 操作 | 管理员 | 员工（`perms.qa=true`） | 员工（`perms.qa≠true`） | 未登录 |
|---|---|---|---|---|
| 看到下拉里的「质量系统」入口 | ✓ | ✓ | ✓ | ✓（登录卡片背后，无下拉） |
| 进入质量系统 | ✓ | ✓ | ✓ | ✗（先登录） |
| 查看异常台账列表 | ✓ | ✓ | ✓ | ✗ |
| 列头排序 / 分页 | ✓ | ✓ | ✓ | ✗ |
| 全选 / 取消全选 / 行选中 | ✓ | ✓ | ✓ | ✗ |
| 导出选中 | ✓ | ✓ | ✓ | ✗ |
| 新增 | ✓ | ✓ | ✗（按钮不渲染） | ✗ |
| 编辑 | ✓ | ✓ | ✗（按钮不渲染） | ✗ |
| 删除 | ✓ | ✓ 且 `perms.acts['qa.del'] !== false` | ✗ | ✗ |
| 筛选（P1） | ✓ | ✓ | ✓ | ✗ |
| 改密 / 退出 | ✓ | ✓ | ✓ | ✗ |

### 7.3 只读用户的按钮形态 —— 决策：**隐藏，不禁用**

- **决策**：只读用户的「新增」「编辑」「删除」按钮**完全不渲染**，与生产系统 `bulkBar` 的 `if(writable){…}` 口径逐字一致（F6）。「全选」「导出选中」正常渲染。
- 理由 1（一致性）：生产系统对"表单级只读"的既有做法就是隐藏写按钮。若质量系统改用禁用态，同一个用户在生产系统看不到按钮、在质量系统看到灰按钮，会产生"是不是这两个系统权限不一样"的误判。
- 理由 2（体验）：灰按钮只能靠 `title` 或点击后的 `alert` 解释原因，是一次无效交互；隐藏 + 一条明确提示，用户一次就懂。
- **必须配套的补偿**：隐藏了按钮就没有任何解释，用户会以为加载失败/系统出错。因此页面顶部固定渲染一条浅色提示条：
  ```
  ⓘ 当前为只读访问（未获「质量管理」编辑权限），如需登记异常请联系管理员在「员工管理 → 表单写权限」中授权。
  ```
  `background:#fef3c7`（浅黄）、`color:#92400e`、12px、圆角 6px、卡片上方、不可关闭。有 `qa` 写权限的用户不渲染此条。
- 不隐藏下拉里的「质量系统」项：若隐藏，用户会以为功能没上线；且下拉里出现一个"点不动的项"体验更差。**所有人都能进，写入受权限控制**。

## 九、给架构师的关键提醒（非需求，但会决定实现成败）

1. **登录态无法跨进程直接校验**：token 存在生产后端内存 `Map` 里（F4）。`qa-server` 必须**代理校验**——把 `Authorization: Bearer` 转发到 `http://127.0.0.1:3000/api/me`，200 则取 `perms` 判权。这是"零改动复用登录"的唯一可行解，且 `/api/me` 已经返回 `perms`（含新增的 `qa` 键与 `perms.acts`）。
2. **nginx 三路由**：`/quality/` → 静态目录；`/api/qa/*` → `127.0.0.1:3001`；其余 `/api/*` → `127.0.0.1:3000`（现有）。路由前缀必须与生产系统的 `/api/*` **不重叠**，否则会劫持生产接口。
3. **禁止用 URL 传 token**：安全基线 P0③ 已明确 token 只走 `Authorization` 头。不要为了"跨系统带登录态"退化回 query token。
4. **禁止 `window.open`**：sessionStorage 按标签页隔离，新标签页必然丢登录态（F1）。
5. **`index.html` 的改动面要锁死**：只允许改 3 处 ——（a）第 301 行 `<h1>` 内的下拉触发结构；（b）顶部 `SYSTEMS` 常量；（c）`PERM_FORMS` + `FORM_ACTS` 各加一行。**不得**为质量系统改动任何表格/权限/启停逻辑函数。
