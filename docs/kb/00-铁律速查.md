## 3. 版本号纪律（2026-11-26 起改为单源）

- **唯一真源**：仓库根 `VERSION` 文件（`BUILD=` / `PREV=` 两行）
- 改版本 = 只改 `VERSION` → `node scripts/version.js sync` 自动写入全部落点 → `check` 自证
  - ⚠ **本文不写"落点共多少处"这类绝对数字**。数量与位置以 `node scripts/version.js list` 为准 —— 写死的数字会随新增测试文件腐化，`.144/.148/.159` 三次假失败全因绝对计数过期
- **禁止**手工逐处改版本号；**禁止**从 `index.html` 反推版本（否则断言退化为恒真）
- **注释**里的版本令牌**只能**写 `【build .NNN】`，**绝不**写完整版本号（有测试按「任意形态正则」统计完整版本号出现次数并断言恰 1 处，注释写完整号直接红）
- 三种形态别混（`YYYY-MM-DD.NNN` 是**占位符**，非真实版本号）：
  - **权威水印** `>build YYYY-MM-DD.NNN<`（带尖括号）：全仓**恰 1 处**，只在 `index.html` 右下角，`deploy.sh` 靠它提取版本
  - **断言字面量** `'YYYY-MM-DD.NNN'`：**由 `sync` 代笔**，不是违规，勿手改
  - **短形态** `YYYY-MM-DD（build .NNN）`：用于 `js/guide.js` 文首与 README

## 4. 业务口径不变量（改动前必读）

- **库存** = Σ(库存订单已交付)；销售已交付恒非负，库存已交付**可负**（欠货）
- **已计划未交付** = Σ交付计划 `planQty` − Σ排产 `done`；**结余** = 已交付 + 已计划未交付。两列同源同规则、**均不钳制** ⇒ 恒等式恒成立。唯一公式点 `invPlannedUndelOf`，**禁止** `Math.max` 钳制回潮
- **报工不改变结余**
- **超排两维度勿混**：订单行级（角标 `invOverPushOf`）vs 交付计划行级（`ppPlannedOfLine` vs `planQty`）。错绑类缺陷**只在计划行级可见**，只看角标会漏检
- 库存订单无"数量"字段，数量 = `stockMax`；分页统一 `slicePaged`
- 已交付 4 档 `invStockLevel`：<0 红 / **0 ≤ v < 最小且最小>0** 黄（闭区间） / 正常绿 / >最大 灰；最小 ≤0 视为不设限

## 5. 单源解析（禁止第二份实现）

- 排产单 → 交付计划：**一律** `ppDlIdxOf(p)`（外键 `deliveryPlanNo` 优先，回退 `deliveryIdx`）
- 排产行 → 交付计划行：**一律** `ppDlRowOf(d,y)`（`dlLine` 命中**且** `productId` 一致 → 否则唯一匹配 → 歧义返 null）
- 凡按行号取行**必须校验 `productId`**
- `applyTransfers(type,moves,opts)` 是调拨台账**唯一**写入器；快照归属：sales 优先 → 双非 sales 取**调入侧** → 仅 in 缺失兜底 out
- `saleRemainCallable` 是全工程唯一可用量公式；`transfer.js` 正文禁出现副本

## 6. 验证可信度（最高优先，违反则结论作废）

1. **"验证通过"必须指向不可变字节**：跑前跑后各取 md5，或 `git show <rev>:<file> | md5sum` 对拍。**别信"某提交"的口头引用**
2. **基线类断言禁用 `HEAD`**：须固定哈希或自动解析改前修订 + **防对消守卫**（两侧必须不同修订）。否则提交后基线与自身对消、守卫退化为恒真
3. **变异注入**必须"命中数恰 1 + 注入必须生效"，**禁止静默跳过 / 宽松匹配 / 多命中取首**
4. **判"线上是否变更"禁用 `cmp` 逐字节**（JSON 键序会变），须按顶层键语义比较
5. 新增守卫必须在**已知会红的输入**上验红一次（否则"写了但永远绿"）
6. **派工验证带时限**：技术方案先自测再派。`git worktree` 隔离实测会让 `node --test` **挂死**（9min CPU 仅 1.17s＝空转非慢；主仓库同套 18s）⇒ 独立回归**在主仓库跑**，派工写明「超 5 分钟无输出＝挂死」
7. **派工即令实现方停手**：验证期间禁新提交，否则验证对象搬家、结论作废

## 7. 变更纪律

- **先分析-不执行**：改动前先只读侦察 + 列影响 + 给 A/B/C 方案，等用户显式确认
- **冻结纪律**：主理人宣告冻结点后，任何源码改动**先报后改**。"改完再说"不等于守边界
- **测试资产与产品代码同等评审**：把缺陷断言成"正确行为"、基线对消、结论漏写前提——这三类**不报错、只让报告看起来全绿**，危险度高于业务 bug
- **迁移脚本三铁律**：① seed 必须深拷贝（防反向污染）② 待上传 `data.json` 用 `JSON.stringify(out,null,1)` + md5 对拍 ③ 差异恒空先怀疑"两侧是同一对象"
- 存量订正范式：`_apply_NNN_*.js`（生产同源沙箱 dry-run）→ 上传 → **重启 `prod-server`**（内存常驻，只改文件会被回写覆盖）→ 再 `deploy.sh`

## 8. 常见陷阱速查

| 现象 | 真因 |
|---|---|
| 回归出现"变异注入失败"假失败 | 用了 `node --test` 目录形式扫到旧快照 → 改用 `bash scripts/test.sh` |
| 部署后"本地 curl 看到旧页面" | 本机透明代理缓存 → 改在服务器本地 curl |
| 台账快照排序错乱 | `ts` 是 `toLocaleString('zh-CN')`，月/日不补零，**禁字符串比较**，用 `tsRankOf` |
| 弹窗把货调给错的库存订单 | 原地 `sort(__csCands)` 导致 `data-ci` 下标错位 → **只许排副本** |
| 拖列后系统默认列序被污染 | 取 `tblLayout` 分片未深拷贝 |
| 新旧前端/接口 404 窗口期 | 部署顺序必须"先后端后前端" |
