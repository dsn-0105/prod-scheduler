# 质量系统首次部署失败 · 根因与修复复盘

> 日期：2026-11-25
> 涉及版本：`build 2026-11-23.163`（生产）/ `build 2026-11-23.001`（质量系统）
> 修复提交：`a412e4e fix(.163)（质量系统）：qa-core require 兼容扁平部署布局`
> 影响范围：**仅质量系统部署中断，生产排单系统零影响**

---

## 0. 一句话结论

`server/qa-store.js` 与 `server/qa-server.js` 里的 `require('../quality/qa-core.js')` 写死了**本地仓库布局**（`server/` 与 `quality/` 是兄弟目录），而 `deploy-qa.sh` 采用的是**服务器扁平布局**（所有后端文件同在 `/opt/qa-server/`）。首次部署在第 3/7 步执行 `--init` 时报 `Cannot find module`。

修复方式：让 `require` 兼容两种布局（先同目录、再回退兄弟目录），并补一条**在部署布局下真跑一次**的冒烟测试——这个不变量此前无人守护。

## 3. 根因：两套目录布局，代码只认一套

### 本地开发布局（`require` 是按这个写的）

```
prod-scheduler/
├── server/
│   ├── qa-server.js    require('../quality/qa-core.js')
│   ├── qa-store.js     require('../quality/qa-core.js')   ← 第 20 行
│   └── qa-auth.js
└── quality/
    └── qa-core.js      ← 兄弟目录，`../quality/` 正好命中 ✅
```

### 服务器部署布局（`deploy-qa.sh` 有意为之）

```
/opt/qa-server/
├── qa-server.js
├── qa-store.js
├── qa-auth.js
└── qa-core.js          ← 与入口同目录，但代码去找 ../quality/ = /opt/quality/ ❌
```

`deploy-qa.sh` 里的注释写明了这是**刻意设计**：

```bash
# ★ qa-core.js 的第二落点：与前端同一份字节（"编号只有一份实现"）
scp -q "${SCP_OPTS[@]}" quality/qa-core.js  "$HOST:$QA_DIR_REMOTE/.incoming/qa-core.js"
```

扁平布局的合理性：服务器上后端所有文件集中一处，备份、权限、日志、systemd `WorkingDirectory` 都简单；且 `qa-core.js` 需要与前端 `/var/www/html/quality/qa-core.js` **字节相同**（编号生成只有一份实现，由脚本的 md5 断言保证）。

**结论：责任在代码，不在部署脚本。** `require` 写死了只适用开发布局。

## 4. 为什么 1141 条测试一条都没拦住

这是本次最值得记录的部分。

| 环节 | 覆盖情况 |
|---|---|
| `qa-store.js` / `qa-auth.js` 单元测试 | 41 条，**全在本地布局下 `require`** |
| `qa-server.js` 端到端测试 | 21 条，**全在本地布局下** |
| `check-syntax.js` | 只做语法解析，不执行 `require` 解析 |
| 部署脚本本地演练 | 只验证 nginx 片段插入/幂等、`bash -n` 语法，**不执行 node 启动** |
| **"部署后的目录结构能否启动"** | **零覆盖** |

一句话：**测了，但测的是另一个世界。**

`require` 的模块解析结果取决于**文件在磁盘上的相对位置**，这是与"代码逻辑"完全正交的一个维度。绝大多数测试天然带着"我在仓库里"这个隐含前提，一旦脱离仓库布局，所有断言都无效。

### 同族教训（本项目此前已踩过两次）

这已经是同一族错误的第三次，前两次：

1. **`grep -c $'\r'` 恒失真**（`build .163` 期间）：该写法在 Git Bash 下把 CR 当行终止符处理，退化为"匹配每一行"，导致纯 LF 文件与真 CRLF 文件给出**同样的数值**（都等于总行数），据此得出"383 行全是 CRLF"的强误导结论。正确口径是 `git ls-files --eol` / `tr -cd '\r' | wc -c` / 直接数 `0x0D`。
2. **守卫依赖字面锚点**：QA 的 `#sysMenu` 结构守卫用 `'<h1 class="sys-switch"'` 定位，工程师修复 P1-2 时把 h1 改成 `sys-switch-trigger`，锚点立刻失配，守卫从"能抓缺陷"退化成"定位失败"却仍报绿。

三次的共同形态：**断言存在、执行通过、但不在真实条件下判别**。

## 5. 修复

### 5.1 代码：`require` 兼容双布局

`server/qa-store.js` 与 `server/qa-server.js` 同步改为（语义完全一致）：

```js
/* 【.163 部署修复】qa-core.js 有两个落点，require 必须兼容两种布局：
   · 本地仓库：server/ 与 quality/ 是兄弟目录 ⇒ ../quality/qa-core.js
   · 服务器部署：deploy-qa.sh 把 qa-core.js 与 qa-server.js 放在同一目录（/opt/qa-server/）
     ⇒ ./qa-core.js
   顺序：先同目录（部署态）、再回退（开发态）。两者字节相同，由 deploy-qa.sh 的 md5 断言保证
   「编号只有一份实现」。禁止复制第二份实现到本文件。 */
const core = (function loadQaCore() {
  const candidates = ['./qa-core.js', '../quality/qa-core.js'];   // 部署态 → 开发态
  let lastErr = null;
  for (let i = 0; i < candidates.length; i++) {
    try { return require(candidates[i]); }
    catch (e) {
      if (!e || e.code !== 'MODULE_NOT_FOUND') throw e;   // 真故障（语法错/运行期异常）立刻抛
      lastErr = e;
    }
  }
  const err = new Error('无法加载 qa-core.js（已尝试同目录 ./qa-core.js 与 ../quality/qa-core.js 两个落点）');
  err.code = 'MODULE_NOT_FOUND';
  err.cause = lastErr;
  throw err;
})();
```

**关键加固：只用 `MODULE_NOT_FOUND` 判定"该落点不存在"。**

如果 `qa-core.js` 存在但自身抛错（语法错误、运行期异常），必须**立刻原样抛出**。否则 `try/catch` 会把真故障伪装成"路径不对"，把排查方向引向错误的地方——**错误信息指向错处，比缺陷本身更耗时间**。

### 5.2 没有改 `deploy-qa.sh`

一个字节都没动。扁平布局保留（运维友好），已上传的文件不必重传。

### 5.3 修复后重跑部署

脚本 7 步全部可重入，直接重跑即可：

| 步 | 上次状态 | 本次行为 |
|---|---|---|
| [2/7] | 已上传 | 重传 + 多一份带时间戳的备份（无害） |
| [3/7] | `--init` 失败 | 数据文件不存在 ⇒ 重新 `--init` ⇒ **成功** |
| [6/7] | marker 0 处 | 走"插入"路径 |

```
A  修复前代码 + 扁平布局  → status=1  err=Cannot find module '../quality/qa-core.js'   ← 证明 §1 不是恒真
```

## 7. 沉淀的纪律

已写入 `tests/README.md`：

> **凡涉及"文件放在哪、如何被找"的改动（`require` 路径 / 部署布局 / systemd `WorkingDirectory` / nginx `root`+`alias`），都必须有一条在目标布局下真跑一次的用例。**

它们属于同一族纪律，建议一起记：

| # | 纪律 | 来源教训 |
|---|---|---|
| 1 | 验证必须指向**不可变字节**（`git ls-files --eol` / `md5sum` / `od -c`），不接受"属性声明"或"看着对" | `grep -c $'\r'` 恒失真 |
| 2 | 任何新增守卫，必须在**一个已知会红的输入**上验红一次，否则不许入库 | 守卫用 `stroke-width` 误命中而恒真；字面锚点随被守护对象一起失效 |
| 3 | 涉及路径/布局的改动，必须在**目标布局下真跑一次** | 本次 `Cannot find module` |

## 8. 部署设计的两项价值验证

本次故障同时验证了两个此前的设计决策是对的：

1. **两步独立部署**：`deploy-qa.sh`（质量系统）与 `deploy.sh`（生产前端）分离。质量系统部署失败时，生产前端与生产后端各一个字节都没动。若打成单一部署包，本次故障会连带影响生产首页。
2. **`nginx -t` 安全闸门**：配置写入后先 `nginx -t`，失败立即用备份还原且**不 reload**。本次故障未走到第 6 步，但同一机制保证"配置写坏不会把生产一起带下去"。
